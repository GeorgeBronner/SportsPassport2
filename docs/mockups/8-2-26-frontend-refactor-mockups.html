Frontend refactor — decision mockups

Companion to docs/8-2-26-frontend-refactor.md. Every variant below is built on the app's real design tokens and the real 235-game log, so what you see is what it would look like shipped. Pick one option per section (or say "neither") and I'll implement.

Toggle light/dark with the button — several of these decisions only make sense in one theme.

Tier 1 · bug 1.1 + 1.2

A · The season chart

One viewBox="0 0 300 110" component, stretched by w-full to whatever its container is. Measured live: 306px in the Stats rail (fine — 1.0×) but 1182×433px on the Map page (3.94×, with 37px axis numbers). Text scales with the box, and the final tick is clipped to '2 everywhere. All three variants below fix the text size and the clipping; they differ in what the chart is for.

A1Fixed height, responsive width Closest to today. One component, honest at any width.

Games per season

In a 320px rail

Same component, same code, two very different widths. Bars re-flow to fill the width; axis text stays 10px in both; the last label is anchored end so '25 survives. Height is pinned at 132px so the Map page stops being eaten by a 433px chart — and so the rails don't blow up when they stack full-width below the lg breakpoint.

A2Sparkline + hover detail Denser. Turns a decorative chart into something you interrogate.

Games per season

Hover any bar → year, count, league split, and your record that season. The year and the count are real; the league split and record in the tooltip are illustrative — the API doesn't break down by season yet, so this variant implies a small backend addition.

A3Heatmap strip Most compact. Frees a whole panel in the rails.

Games per season

34 years in ~40px of height, legible down to 200px wide, and it matches the ink-depth language the Stats tile map already uses. Trades exact magnitude for compactness.

My recommendation: A1 for the fix (it's a drop-in replacement everywhere), plus A2's hover layered on top. A3 is worth it only if you want the rails to carry more panels.

Tier 1 · bug 1.5

B · Dark logos on dark panels

Switch this page to dark to see the problem. Roughly a quarter of pro-league rows have a black or navy primary mark that disappears against --panel. The logos load fine — they're just invisible.

B0Today — no treatment Spurs and Ducks read as blank gaps in dark mode.
B1Light plate behind every badge Uniform, predictable, no per-logo logic. Slight "sticker" look.

A single rule: in dark mode every badge sits on a soft near-white rounded plate. Applies to all leagues equally, so the badge column stops looking ragged. One line of CSS.

B2Contrast ring / halo Keeps logos on the panel, but only rescues outlined marks.

A 1px white drop-shadow traced around the artwork. Beautiful on marks with a defined silhouette (Ducks, Saints); does almost nothing for a solid black roundel (Spurs).

B3Per-logo plate, decided at scrape time Best-looking. Needs a backend column + re-scrape.

Compute mean luminance when fetch_team_logos.py downloads the PNG and store a logo_is_dark flag; only those teams get the plate. Bright logos (Alabama crimson, Heat red) stay clean on the panel. Costs a migration and a re-run of the scrape.

My recommendation: B1 now — it's a one-line CSS fix that solves 100% of the cases. B3 later if the uniform plate bothers you.

Tier 2 · gap 2.3

D · The Find home page

At a 1768×942 viewport the front door ends 518px down — 45% of the height empty — in a 768px column inside a 1280px shell, so 57% of the width is unused too. Everything below uses endpoints the page could already call. All three keep the omnibox as the hero.

D1"On this date" + recent stamps Gives the page a reason to be revisited. Personal, not statistical.
D2Passport summary strip Turns the landing page into a dashboard. Duplicates the Stats page.
D3Upcoming games for your teams The most useful — and the only one needing a new endpoint.
My recommendation: D1. It's the only one that makes the home page feel like yours rather than a search box, and it needs no backend work. D3 is the strongest idea overall but wants a GET /api/games/upcoming first.

Tier 2 · gap 2.4

E · The My log ledger

235 rows, one flat list, no filter of any kind — while Find and Map both have league chips. Plus ~270px of dead gutter in every row between the venue and the buttons.

E1Filter bar + filled gutter Same row height, more information, and the list becomes navigable.
E2Grouped by season, actions on hover Calmer. Trades instant access to Remove for much less visual noise.
My recommendation: E1's filter bar is non-negotiable at 235 rows; E2's hover-reveal for Remove is worth stealing either way — a destructive action shouldn't be permanently visible 235 times.

Tier 2 · gap 2.8

F · "Teams seen most"

Alabama 149 vs. everyone else (29, 17, 14, 13, 12, 11, 10). On a linear scale against 149 every other bar is a sliver, so the chart says nothing. It also drops the logos used everywhere else.

F0Today — linear vs. the max Ranks 2–8 are indistinguishable.
F1Logos + linear vs. the runner-up Leader breaks the scale on purpose; the field stays readable.
F2Square-root scale Honest at both ends, but no one reads a sqrt axis.
My recommendation: F1. Alabama at 149 in a 235-game log is the story — let it max out and let the other seven be comparable to each other.

Tier 3 · idea 3.3

G · Shading the map

The Map already draws state boundaries but fills every state identically. The Stats page already computes games_by_state and shades a tile grid with it. Using the same scale on the real map costs nothing and makes the two views speak the same language.

G0Today — flat fill
G1Choropleth + dots

Schematic — real geometry comes from the existing usOutline.ts projection. The question is only whether you want the fill at all, and if so whether the dots stay on top.

My recommendation: G1, with the fill kept deliberately low-contrast so the league-coloured dots still read as the primary layer.
